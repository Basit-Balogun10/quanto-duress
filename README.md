# Quanto Duress

Quanto is a mobile-first banking prototype built around **duress access** and **silent failure**. It is designed to explore how a banking interface can protect a customer when they are being coerced, without making the protection obvious to the person applying pressure.

**Live demo:** https://quanto-duress.pages.dev

The demo is a browser-local prototype. It uses simulated money, simulated accounts, and synthetic transaction data. It does not connect to real bank accounts or move real funds.

## What It Demonstrates

- **Local multi-user signup** with separate accounts, balances, PINs, and activity per browser.
- **Duress access** with a separate duress PIN, capped or percentage-based decoy balance, and optional decoy history.
- **Silent failure** triggered by three sharp shakes, a wake phrase, holding the logo, or entering the duress PIN during a transfer.
- **Hidden recovery:** while silent failure is active, hold the Quanto logo for 2.5 seconds to open the recovery PIN dialog. The failed-transfer screen also exposes a normal-looking "Restore connection" flow.
- **Decoy ledgers** generated by AI, pre-warmed in the background as soon as duress access is configured, cached per account, validated for schema and balance, and never used to determine what really happened to the customer's money.
- **Subtle caught cue:** a quiet two-note sound by default, a short double pulse on supported devices, and a brief, faint dot near the top-right of the screen. Sound can be muted for vibration/dot only, and the cue can be previewed in Settings.

## Demo Flow

1. Open the live demo and create an account.
2. Tap **Add test money** to fund the demo account.
3. In **Settings**, enable duress access with a duress PIN and a decoy balance.
4. Enable silent failure and choose one or more triggers.
5. Use **Test cue** to preview the caught cue.
6. Trigger silent failure by shaking the phone, saying the wake phrase, holding the logo, or entering the duress PIN on a transfer.
7. Verify that transfers fail with a realistic network error and that no money leaves the account.
8. Recover by holding the logo while silent failure is active, or by using **Restore connection** on the failed-transfer screen, then enter the recovery PIN.

While silent failure is active, Settings deliberately looks untouched: the silent-failure controls appear off and the network-unavailable card is not shown.

## Architecture

```text
React + Vite + TypeScript
        |
        |  decoy ledger request
        v
Cloudflare Worker  --->  OpenAI-compatible API
        |            \
        |             --->  Workers AI fallback
        v
Cloudflare D1 cache
```

- The banking UI, account state, PIN verification, balances, caps, and transfer rules are deterministic client-side logic.
- Account data is stored in browser storage under an account-scoped key.
- The Worker generates and caches decoy ledgers. It never receives the customer's real balance, PIN, duress settings, or trigger state.
- After duress setup, the client pre-warms the matching decoy ledger before it is needed. A cold or failed pre-warm falls back to the deterministic ledger.
- The trigger cue plays a quiet two-note sound by default. Mute keeps the short vibration and top-right dot only; browsers that require a user gesture prime audio on the next tap or keypress.
- OpenAI `gpt-5.4-mini` is the primary decoy generator. Workers AI is used as a fallback when the external provider is unavailable.
- Generated ledgers are validated before caching. If AI generation fails, the app falls back to a deterministic decoy ledger.

## Responsible AI Use

AI is used for a deliberately narrow purpose: **generating realistic synthetic decoy transaction histories** so a duress balance looks plausible.

- **AI is not trusted with security decisions.** It does not detect triggers, verify PINs, choose duress caps, move money, change balances, or clear silent failure.
- **AI output is not authoritative.** Every generated ledger is parsed, schema-checked, and balance-checked before use.
- **There is a deterministic fallback.** If the model is unavailable, slow, or returns invalid output, a locally generated ledger is used instead.
- **No real customer or banking data is sent to the model.** Prompts contain only synthetic values needed to shape a decoy history.
- **The model has no tools or autonomous actions.** It returns JSON only; the application decides whether and how to use it.
- **Secrets stay server-side.** The OpenAI key is stored as a Cloudflare Worker secret and is never included in the client bundle.
- **The product is explicit about its limits.** It is a prototype for testing safety ideas, not a production banking system.

## Local Development

Requirements: Node.js 22+, pnpm, and optionally a Cloudflare account for remote deployment.

```bash
pnpm install
```

Frontend:

```bash
cp .env.example .env
pnpm dev
```

The app runs at `http://127.0.0.1:5173`.

Worker:

```bash
pnpm worker:dev
```

Create `.dev.vars` in the repository root with the Worker configuration:

```dotenv
AI_API_KEY=your_openai_key
AI_BASE_URL=https://api.openai.com/v1
AI_MODEL=gpt-5.4-mini
WORKERS_AI_MODEL=@cf/meta/llama-3.3-70b-instruct-fp8-fast
AI_REASONING_EFFORT=high
ALLOWED_ORIGINS=http://localhost:5173,http://127.0.0.1:5173
```

`.dev.vars` and `.env` are gitignored. Do not commit secrets.

Apply the D1 migration locally:

```bash
pnpm exec wrangler d1 migrations apply quanto-decoy --local
```

## Security Notes and Limitations

This is a competition prototype, not a production banking system.

- Accounts, PINs, and transaction history are stored locally in the browser.
- There is no server-side authentication or account recovery service.
- The PIN is four digits and is not protected by a hardware-backed keystore.
- The duress and silent-failure flows are designed for demonstration and testing.
- AI-generated decoy ledgers are synthetic and visibly separate from authoritative state in the data model.
- Browser vibration support varies. iOS Safari does not expose the Vibration API, so the visual cue is the fallback there.
